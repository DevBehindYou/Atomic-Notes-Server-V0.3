# Read-only history retention inspection

`npm run db:inspect-ledger-history` reports account/row counts, accounts over 50 entries, potentially removable rows, largest history, orphan history, and archived/recent statistics counts. It prints no account IDs, notes, balances, database names, connection information or driver errors. All arguments are rejected before importing the database runtime; there is no apply mode.

Data counts share a snapshot. Index/catalog readiness is a later separate read. Missing collections remain missing. An exact full ordering index is reported as a prerequisite, not created. Orphan rows are reported for review, not silently discarded. The report always says activationReady=false because rollout readiness cannot be established by database counts alone.

Readiness now distinguishes the full legacy {userId:1,createdAt:-1,_id:-1} index from the full sequence {userId:1,historySequence:-1} index. Both must be usable, not partial/sparse/hidden/collated/TTL. The sequence candidate must be non-unique so multiple unsequenced legacy records remain valid. Compound key order is exact. Disposable fixtures manually build/drop both indexes and prove that inspection reports readiness without changing data, wallets or indexes; activationReady remains false even with both indexes. Pure option checks cover unsupported index variants. This checks catalog shape, not sequence integrity, measured production query cost or authorization to build either index.

This report is a rehearsal/preflight building block. Snapshot aggregates may scan a large ledger; no production query has been run and no performance promise is made. RemovableRows is a snapshot estimate including orphan partitions; it is not authorization to delete that count. The next step is a bounded, resumable migration rehearsal, then index/performance and cutoff tests, writer-overlap prevention, verified backup/restore and an approved production preflight.

Integrity counts now share that data snapshot. Wallet checks detect invalid UUID identities, unsupported markers/counters, and marked histories over 50 or without a contiguous safe-integer tail up to the counter. Each marked wallet lookup is bounded to 51 metadata rows; an over-limit account is flagged even if a larger history cannot be fully classified from that sample. A streaming full-ledger pass uses the current energyLedgerSchema, counts orphan rows, and finds sequence-bearing rows on unmarked wallets anywhere in their history. No full owner history or ID list is retained in memory or emitted. Invalid/unmarked/orphan categories can overlap; counts must not be added as a count of unique affected users or deletable records.

This remains inspection, not repair/quarantine. Anomalies block the reported preflight and remain untouched. Schema checks are the current code contract, not proof of correct historic balances, receipt/lot consistency, archive projections or authorization. Snapshot scans and owner lookups can be expensive; production workload, lookup indexes and transaction-duration limits need separate review. These are characterization tests of added diagnostics, not a reproduced production failure. No production query or migration is run by this change.

Controlled snapshot check: pause after the initial history aggregate has established its transaction snapshot, commit a real synthetic Controller energy credit and then corrupt that fixture's marker, and resume the integrity scan. Every data section must still equal the earlier report; the next independent report must detect the new row and invalid marked wallet. Catalog readiness is still a separate later read. The fixture restores its marker afterward. This proves the controlled interleaving, not arbitrary production workload behavior.

## Additive financial provenance coverage

The same inspect-only command also counts surviving explicit references in `energy_ledger.coinOperationId` and `energy_ledger.lotIds`, `coin_operations.allocations`, and `coin_lots.operationId`. Missing referenced records, foreign-owner references, malformed receipts/lots, orphan owners, and marked-wallet scalar versus lot-total mismatches have separate count fields and blockers. Valid string references are checked independently of whole-record schema validity: a malformed amount, receipt result, or other field does not hide a missing/foreign stored reference. Invalid reference values never become inferred links. A receipt with no ledger entry or allocations can be a legitimate no-op. A `:opening` lot from legacy migration or welcome initialization intentionally has no operation receipt. `legacy` and `controller` lot sources remain unclassified for paid versus promotional policy; this report never assigns either class by guessing from time, amount, or a fingerprint.

The archive section reports lifetime `byKind` totals from `ledger_history_archives` as aggregate-only counts. Archived row IDs, original details, and missing historical causal links cannot be reconstructed from those totals. Existing coin operation receipts and lots support replay and current allocation checks, but are not a complete financial event log. `retainedRowsWithoutExplicitReferences` includes legacy rows whose provenance remains unknown. Counts can overlap and do not establish all-time completeness, correct balances, purchase verification, or an approved retention policy. `activationReady` remains false; B06/B26 policy and writer decisions remain separate.

TTL catalog counts cover `energy_ledger`, `coin_operations`, `coin_lots`, and `sync_operations`. The exact old 30-day `sync_operations.createdAt_1` definition uses the existing transition's shared predicate and is reported separately as a known transition; unexpected TTL definitions are blockers. The catalog read is outside the data snapshot, and this command never changes indexes. Aggregation cursors stream records in batches of 100; each reference/owner/lot-total lookup emits at most one aggregate count record and does not issue a client query per reference. Duplicate references do not count as missing records. Snapshot scans and server-side joins may still be expensive on large databases; production query cost needs separate review.

Reference arrays are sanitized into transient aggregation fields and joined through `localField`/`foreignField: '_id'`, followed by a count-only foreign pipeline. This uses MongoDB's documented [array equality join](https://www.mongodb.com/docs/v7.0/reference/operator/aggregation/lookup/) rather than a correlated `$expr: $in` predicate. No transient fields are persisted or reported. The fixture captures the actual production pipelines and explains all four reference joins with `executionStats`. It requires the foreign `_id` index, zero foreign collection scans, and bounded document/key examinations with 24 then 48 matching source records while unrelated foreign records grow from 200 to 1600. A client command budget alone is not evidence of indexed server work.

Verification is limited to pure checks and disposable fixture scenarios. The additive provenance fixture is registered in `npm run test:integration`, accepts disposable localhost replica sets (including CI port 27017 and local port 27139), uses only a generated `atomic_test_*` database, refuses an existing collection namespace, and drops only the database it owns. The current equality-join revision and its explain assertions still need a successful MongoDB integration run before acceptance; local driver connections timed out during this handoff.
